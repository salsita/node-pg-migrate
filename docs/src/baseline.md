# Adopting an Existing Database

node-pg-migrate builds a database by running its migrations in order, from the first one. A
database that node-pg-migrate didn't create (by hand, with another tool, or with an ORM) has no
first migration. `node-pg-migrate baseline` writes one: a single SQL migration that creates the
schema the database has today.

- Databases that already have that schema, such as production, **record** the baseline without
  running it.
- Blank databases, such as CI or a new developer's machine, **run** it like any other migration.

From then on, you write ordinary migrations and they run everywhere.

## Quick Start

1. Generate the baseline from a database that has the schema. `baseline` connects the way
   `up` does (`DATABASE_URL`, your [config](cli#database-connection) or the `PG*` variables),
   runs `pg_dump --schema-only`, and only reads the database:

   ```console
   $ node-pg-migrate baseline
   > Wrote migrations/1789084800000_baseline.sql
   > On databases that already have this schema, record it without running it:
   >   node-pg-migrate up 1789084800000_baseline --fake
   > Blank databases run it with a normal `node-pg-migrate up`.
   ```

   Commit the file.

2. On every database that already has the schema, run the printed command once:

   ```sh
   node-pg-migrate up 1789084800000_baseline --fake
   ```

   `--fake` records the migration in the migrations table without running it. From then on,
   `up` only runs the migrations that come after the baseline there.

3. On blank databases, run `up` as usual:

   ```sh
   node-pg-migrate up
   ```

   The baseline creates the schema, and the migrations after it run in the same transaction.

New migrations (`node-pg-migrate create …`) sort after the baseline.

> [!TIP]
> Ran `up` without `--fake` on a database that already has the schema? Nothing changed: the
> baseline has no `DROP` statements, so it fails at the first object that already exists
> (`… already exists`) and rolls back. Record it with the `--fake` command, then run `up` again.

## What the Baseline Contains

The schema, and nothing else. `baseline` runs pg_dump like this, and leaves out the migrations
table and its sequence, which node-pg-migrate creates itself:

```sh
pg_dump --schema-only --no-owner --no-privileges --no-publications --no-subscriptions \
  --no-security-labels --no-tablespaces --lock-wait-timeout=10s
```

So the baseline has:

- every object pg_dump dumps: schemas, extensions, types, tables, constraints, indexes,
  sequences, functions, triggers, views, policies, comments, …;
- no rows, and sequences start again from their start value;
- no owners and no grants: objects belong to the role that runs the migration;
- no roles, since they belong to the server rather than to a database. If the schema refers
  to roles (in a policy, for example), create them on blank servers first, e.g. from
  `pg_dumpall --roles-only`.

The file starts with a header, followed by the cleaned-up dump:

```sql
-- Up Migration
-- Baseline generated by `node-pg-migrate baseline` from PostgreSQL 18.6 (pg_dump 18.6).
-- On databases that already have this schema, record it without running it:
--   node-pg-migrate up 1789084800000_baseline --fake
-- Blank databases run it with a normal `node-pg-migrate up`.
```

A few things to know before you run it on blank databases:

- There's no down migration: `node-pg-migrate down` stops at the baseline with
  `User has disabled down migration on file: …`.
- Materialized views are created `WITH NO DATA`, so refresh them after the first run. The
  header says so when there are any.
- Blank databases need the source's PostgreSQL major version or a newer one: pg_dump's output
  isn't guaranteed to load into an older server.
- `CREATE EXTENSION` needs privileges: the role that runs `up` must be a superuser, or have
  `CREATE` on the database for trusted extensions.

## What the Cleanup Changes, and Why

A pg_dump output saved as a migration fails, or leaks settings into the migrations that run
after it. `baseline` keeps pg_dump's output byte for byte, except for:

| pg_dump writes                                                                           | The baseline                                            | Why                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `\restrict <key>` at the top, `\unrestrict <key>` at the end                             | drops both lines                                        | Since the August 2025 minor releases (CVE-2025-8714), pg_dump writes these psql commands into every plain-text dump. They aren't SQL: the server rejects the migration at the first one (`syntax error at or near "\"`). Lines starting with `\` inside a function body are kept. |
| `SELECT pg_catalog.set_config('search_path', '', false);`                                | drops it                                                | It empties the search path for the whole session, and `up` runs all pending migrations on one connection: the next migration would fail with `no schema has been selected to create in`. The dump names every object with its schema, so it doesn't need it.                      |
| `SET statement_timeout = 0;`, `SET lock_timeout = 0;` and the other `*_timeout` settings | drops them                                              | Your own timeouts should apply. `transaction_timeout` (pg_dump 17 and newer) would also fail on PostgreSQL 16 and older.                                                                                                                                                          |
| the other `SET`s, e.g. `SET check_function_bodies = false;`                              | `SET LOCAL`, and restores the previous value at the end | The baseline needs them (a `LANGUAGE sql` function can only refer to a table created after it with `check_function_bodies` off), but the migrations after it get their own settings back.                                                                                         |
| `COMMENT ON EXTENSION …`                                                                 | drops it                                                | Only the extension's owner can run it, so it fails where the extension already exists under another role, which is common on managed PostgreSQL. `CREATE EXTENSION` sets the comment anyway.                                                                                      |
| `CREATE SCHEMA public;` and its default comment                                          | drops them                                              | Every database already has them.                                                                                                                                                                                                                                                  |
| `CREATE SCHEMA <schema>;` for the migrations schema or a `--schema`                      | `CREATE SCHEMA IF NOT EXISTS <schema>;`                 | `up --create-schema` or `--create-migrations-schema` may create it before the baseline runs.                                                                                                                                                                                      |

It never contains `DROP` statements, which is why running it without `--fake` fails safely:
with pg_dump's `--clean`, it would drop your tables first. Dumps that it can't use are refused
rather than fixed: table data, `DROP`s, `CREATE DATABASE` and `\connect`, the migrations table,
and lines that node-pg-migrate would read as `-- Up Migration` or `-- Down Migration` markers
(see [When `baseline` Refuses](#when-baseline-refuses)).

## Options

Run `node-pg-migrate baseline --help` for the full list.

| Option                        | Default              | Description                                                                                                                                                               |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[name...]`                   | `baseline`           | The migration name, after the prefix. Dashes replace spaces and underscores, like `create`: `baseline initial schema` writes `…_initial-schema.sql`.                      |
| `-m`, `--migrations-dir`      | `migrations`         | Where to write the baseline. It is created if it's missing, and must not have any file yet (files starting with `.`, such as `.gitkeep`, don't count).                    |
| `--migration-filename-format` | `timestamp`          | The file name prefix: `timestamp`, `utc` or `index`, like `create`.                                                                                                       |
| `-t`, `--migrations-table`    | `pgmigrations`       | The migrations table. `baseline` checks that it records no migration, and leaves it and its sequence out of the dump.                                                     |
| `--migrations-schema`         | the first `--schema` | The schema of the migrations table.                                                                                                                                       |
| `-s`, `--schema`              | `public`             | node-pg-migrate's schemas, as for `up`. They don't limit what is dumped: that's `--include-schema`.                                                                       |
| `-d`, `--database-url-var`    | `DATABASE_URL`       | The environment variable with the connection string.                                                                                                                      |
| `--reject-unauthorized`       | `undefined`          | Sets the SSL `rejectUnauthorized` option, as for `up`.                                                                                                                    |
| `--from-file`                 | `undefined`          | Clean up this `pg_dump --schema-only` output instead of running pg_dump; `-` reads standard input. See [Using a Dump You Made Yourself](#using-a-dump-you-made-yourself). |
| `--pg-dump`                   | `pg_dump`            | The pg_dump to run, from the `PATH` by default. See [pg_dump](#pg-dump).                                                                                                  |
| `--include-schema`            | every schema         | Only dump these schemas (pg_dump `--schema`). See [Choosing Schemas](#choosing-schemas).                                                                                  |
| `--exclude-schema`            | none                 | Leave these schemas out (pg_dump `--exclude-schema`).                                                                                                                     |
| `--lock-wait-timeout`         | `10s`                | How long pg_dump waits for a table lock before it gives up (pg_dump `--lock-wait-timeout`). See [Waiting for Locks](#waiting-for-locks).                                  |
| `--format`                    | `sql`                | `sql`, or `ts` or `js` to write `pgm` calls instead, see [Experimental: TypeScript and JavaScript Output](#experimental-typescript-and-javascript-output).                |
| `--strict`                    | `false`              | With `--format ts` or `js`: fail instead of writing raw SQL fallbacks. Refused with `--format sql`.                                                                       |
| `-f`, `--config-file`         | `undefined`          | The file with the connection and settings, as for `up`. `--config-value` and `--envPath` work the same way too.                                                           |

Settings from your [configuration](cli#configuration) (`migrations-dir`, `migrations-table`,
`migrations-schema`, `schema`, `migration-filename-format`, the `db` connection) apply as they
do for `up`. To run it from code, see [`baseline()`](api#baseline).

## Using a Dump You Made Yourself

When pg_dump can't run where node-pg-migrate does (no client tools, no route to the database,
a pg_dump older than the server), make the dump elsewhere and pass it with `--from-file`. For
example, with the pg_dump inside the database's Docker container, which always matches the
server:

```sh
docker exec my-postgres pg_dump -U postgres --schema-only --no-owner --no-privileges app > schema.sql
node-pg-migrate baseline --from-file schema.sql
```

`-` reads the dump from standard input:

```sh
docker exec my-postgres pg_dump -U postgres --schema-only --no-owner --no-privileges app \
  | node-pg-migrate baseline --from-file -
```

- Make a plain-text dump (pg_dump's default format) with `--schema-only`, and without
  `--clean` or `--create`. Add `--no-owner --no-privileges` like `baseline` does: owners and
  grants refer to roles that blank servers may not have. If you only have a custom-format dump
  (`-Fc`), turn it into SQL first:
  `pg_restore --schema-only --no-owner --no-privileges -f schema.sql app.dump`.
- The database connection is optional with `--from-file`. When there is one, `baseline` still
  refuses a database that has a migration history, and sizes the
  [`max_locks_per_transaction`](#large-schemas) advice with its `max_connections`. Without
  one, it skips the check and assumes 100 connections.
- `--pg-dump`, `--include-schema`, `--exclude-schema` and `--lock-wait-timeout` only apply
  when `baseline` runs pg_dump itself: pass pg_dump's own options when you make the dump.

## pg_dump

`baseline` runs `pg_dump` from your `PATH`, or the one you pass with `--pg-dump`:

```sh
node-pg-migrate baseline --pg-dump /usr/lib/postgresql/18/bin/pg_dump
```

pg_dump can't dump a server of a newer major version than its own, so `baseline` checks
`pg_dump --version` first and stops with `PG_DUMP_TOO_OLD` when it's older than the server.
Install the client tools of the server's major version (or newer), pass that pg_dump with
`--pg-dump`, or [make the dump yourself](#using-a-dump-you-made-yourself).

pg_dump gets the connection through the environment (`PGHOST`, `PGPORT`, `PGUSER`,
`PGPASSWORD`, `PGDATABASE`, `PGSSLMODE`), never through its command line, where other users of
the machine could see it (in `ps`, for example). Settings your connection doesn't give fall
back to pg_dump's defaults and your environment, such as `~/.pgpass`. An `sslmode` in the
connection string is passed on; an `ssl` object in your config becomes `verify-full`, or
`require` with `rejectUnauthorized: false`.

### Waiting for Locks

pg_dump takes an `ACCESS SHARE` lock on every table it dumps. It only conflicts with
`ACCESS EXCLUSIVE` locks, which most `ALTER TABLE`s, `DROP TABLE`, `TRUNCATE` and
`VACUUM FULL` take (so does a migration that changes a table). Reads and writes carry on while
pg_dump runs; statements that need an `ACCESS EXCLUSIVE` lock on a dumped table wait until it's
done.

If another session holds such a lock, pg_dump waits up to `--lock-wait-timeout` (`10s` by
default) and then `baseline` stops with `PG_DUMP_FAILED`, saying that another session holds a
lock. Retry once that session is done, or wait longer:

```sh
node-pg-migrate baseline --lock-wait-timeout 2min
```

The value takes any format `SET statement_timeout` accepts, e.g. `500ms`, `30s` or `2min`.

## Choosing Schemas

By default, the baseline has every schema but the system ones. `--include-schema` and
`--exclude-schema` choose, with each name matched exactly (no patterns):

```sh
node-pg-migrate baseline --include-schema app audit
node-pg-migrate baseline --exclude-schema scratch
```

> [!WARNING]
> Extensions need their schema. pg_dump creates an extension `WITH SCHEMA` the schema it lives
> in, so a blank database can only create it when the baseline creates that schema too, or
> when it's `public`.
>
> - With `--include-schema`, the baseline keeps the extensions that live in an included schema
>   or in `public` (with pg_dump 14 or newer). `baseline` warns about the ones it leaves out:
>   include their schema, or create them on blank databases before the baseline runs.
>   pg_dump 13 and older can't dump extensions together with `--include-schema`, so the
>   baseline then has none, and `baseline` warns about that.
> - With `--exclude-schema`, pg_dump still dumps every extension, even one that lives in an
>   excluded schema. `baseline` warns when that happens: blank databases need that schema
>   before the baseline runs.

## Large Schemas

The baseline creates everything in one transaction, and PostgreSQL keeps a lock on every
relation it creates (tables with their TOAST table and index, indexes, sequences, views) until
the transaction ends. The shared lock table has room for about `max_locks_per_transaction`
locks per connection (`max_connections` plus `max_prepared_transactions`): 6,400 with the
defaults. A larger schema fails on a blank database with `out of shared memory` (`53200`), and
a hint to increase `max_locks_per_transaction`.

`baseline` estimates how many relations the migration creates. When a blank database needs
more than the default of 64, it prints a warning with the value, and the header repeats it:

```sql
-- It creates about 40,500 relations in one transaction, so blank databases need
--   max_locks_per_transaction = 512 or more (the default is 64).
```

Set it on the servers that run the baseline from scratch, such as CI. It needs a restart:

```sh
# postgresql.conf, or ALTER SYSTEM SET max_locks_per_transaction = 512; then restart
docker run -e POSTGRES_PASSWORD=postgres postgres:18 -c max_locks_per_transaction=512
```

The estimate uses the source server's `max_connections`; a server with fewer connections needs
more. Databases that record the baseline with `--fake` don't create anything, so they don't need
it.

For scale: a schema of 5,000 tables (about 40,000 relations, a 9 MB dump) dumped in about two
seconds, the cleanup took well under a second, and applying the baseline to a blank database
took about 30 seconds, which is PostgreSQL running the DDL. It needed
`max_locks_per_transaction = 512`.

## When `baseline` Refuses

When the options, the database or the dump can't make a baseline, `baseline` exits with code 1
and prints a message that says what's wrong and what to do. It writes no file. From code,
[`baseline()`](api#baseline) throws a `BaselineError` with one of these codes:

| Code                       | When                                                                                                                                   | What to do                                                                                                                                                                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MIGRATIONS_EXIST`         | The migrations directory already has a file (`… already has 1 file(s)`).                                                               | A baseline is the first migration: write it to a new or empty directory with `-m`. A project that already uses node-pg-migrate doesn't need one.                                |
| `HISTORY_EXISTS`           | The migrations table records migrations (`"public"."pgmigrations" already records 3 migration(s)`).                                    | node-pg-migrate already manages this database: keep writing migrations. If that's unexpected, check `--migrations-table` and `--migrations-schema`, and which database you use. |
| `UNSUPPORTED_SERVER`       | The server is CockroachDB.                                                                                                             | See [CockroachDB](#cockroachdb).                                                                                                                                                |
| `PSQL_META_COMMAND`        | The dump has a psql command other than the `\restrict` pair, such as `\connect app`.                                                   | `\connect` comes from pg_dump's `--create`: dump without it. Take any other psql command out of the dump.                                                                       |
| `DATA_IN_DUMP`             | The dump has table data (`COPY … FROM stdin`).                                                                                         | Dump with `--schema-only`.                                                                                                                                                      |
| `CREATE_DATABASE`          | The dump creates a database.                                                                                                           | Dump without `--create`.                                                                                                                                                        |
| `CLEAN_DUMP`               | The dump drops objects.                                                                                                                | Dump without `--clean`.                                                                                                                                                         |
| `MIGRATIONS_TABLE_IN_DUMP` | The dump creates the migrations table or its sequence.                                                                                 | Leave them out of the dump with the `--exclude-table` the message names.                                                                                                        |
| `MARKER_COLLISION`         | A line starts like `-- Up Migration` or `-- Down Migration`, e.g. in a function body: node-pg-migrate would split the migration there. | Change that line in the object it comes from (e.g. with `CREATE OR REPLACE FUNCTION`), then run `baseline` again.                                                               |
| `PG_DUMP_NOT_FOUND`        | pg_dump isn't on the `PATH` or at `--pg-dump`.                                                                                         | Install the PostgreSQL client tools, pass `--pg-dump <path>`, or use `--from-file`.                                                                                             |
| `PG_DUMP_TOO_OLD`          | pg_dump is older than the server, e.g. pg_dump 16 for PostgreSQL 18.                                                                   | Use a pg_dump of the server's major version or newer, see [pg_dump](#pg-dump).                                                                                                  |
| `PG_DUMP_FAILED`           | pg_dump failed. The message quotes its first error lines, or says that it couldn't lock a table in time.                               | Fix what pg_dump reports. For locks, see [Waiting for Locks](#waiting-for-locks).                                                                                               |
| `INVALID_OPTIONS`          | The options can't work together, e.g. no connection and no `--from-file`, or `--format ts` with `--from-file`.                         | Fix the options as the message says.                                                                                                                                            |
| `UNSUPPORTED_OBJECTS`      | `--format ts` or `js` only: the database has objects that can't be written that way, or `--strict` found fallbacks.                    | See [Experimental: TypeScript and JavaScript Output](#experimental-typescript-and-javascript-output).                                                                           |

Without any connection (no `DATABASE_URL`, `db` config or `PG*` variables) and without
`--from-file`, `baseline` stops the way `up` does:
`The DATABASE_URL environment variable is not set or incomplete connection parameters are provided.`

## CockroachDB

`baseline` supports PostgreSQL only, and refuses CockroachDB servers (`UNSUPPORTED_SERVER`). To
adopt a CockroachDB database, write the first migration yourself and record it the same way,
with `node-pg-migrate up <name> --fake`.

## Experimental: TypeScript and JavaScript Output

> [!WARNING]
> `--format ts` and `--format js` are experimental. Review the generated migration before you
> commit it, and expect the output to change between releases. The SQL baseline is the one to
> rely on.

```sh
node-pg-migrate baseline --format ts
```

Instead of running pg_dump, `baseline` reads the database's catalogs (read-only, with the same
few queries however large the schema is) and writes a migration made of `pgm` calls:
`migrations/<prefix>_baseline.ts` (or `.js`), with `export const down = false`. It prints
`> Note: --format ts is experimental; review the generated migration.`, and the file's header
says so too. The rest works like the SQL baseline: record it with the printed `--fake`
command, run it on blank databases with `up`.

For the [Chinook](https://github.com/lerocha/chinook-database) sample database, it writes this
(`// …` marks what is left out here: the other tables, keys, foreign keys and indexes):

<!-- prettier-ignore -->
```ts
// Baseline generated by `node-pg-migrate baseline --format ts` from PostgreSQL 18.6.
// --format ts is experimental: review this migration before you rely on it.
// On databases that already have this schema, record it without running it:
//   node-pg-migrate up 1789084800000_baseline --fake
// Blank databases run it with a normal `node-pg-migrate up`.

import type { MigrationBuilder } from 'node-pg-migrate';

export const up = (pgm: MigrationBuilder): void => {
  pgm.sql('SELECT pg_catalog.set_config(\'node_pg_migrate.check_function_bodies\', pg_catalog.current_setting(\'check_function_bodies\'), true);');
  pgm.sql('SET LOCAL check_function_bodies = false;');

  pgm.createTable('album', {
    album_id: 'serial',
    title: { type: 'character varying(160)', notNull: true },
    artist_id: { type: 'integer', notNull: true },
  });

  pgm.createTable('artist', {
    artist_id: 'serial',
    name: 'character varying(120)',
  });

  // …

  pgm.addConstraint('album', 'album_pkey', 'PRIMARY KEY (album_id)');

  // …

  pgm.addConstraint(
    'album',
    'album_artist_id_fkey',
    'FOREIGN KEY (artist_id) REFERENCES public.artist(artist_id)'
  );

  // …

  pgm.createIndex('album', ['artist_id'], { name: 'album_artist_id_idx' });

  // …

  pgm.sql('SELECT pg_catalog.set_config(\'check_function_bodies\', pg_catalog.current_setting(\'node_pg_migrate.check_function_bodies\'), true);');
};

export const down = false;
```

- It needs a database connection, so `--from-file` doesn't work with it (`INVALID_OPTIONS`).
  `--include-schema` and `--exclude-schema` apply, but extensions are kept whatever their
  schema (blank databases need it, see [Choosing Schemas](#choosing-schemas)), and
  `--include-schema` leaves out casts, which belong to no schema. `--pg-dump` and
  `--lock-wait-timeout` don't apply.
- Names are relative to the first `--schema` (`public` by default); objects in other schemas
  are written as `{ schema, name }`. Column defaults are written as `pgm.func(…)`, exactly as
  PostgreSQL stores them.
- Like the SQL baseline, it turns `check_function_bodies` off while it runs (the first and
  last `pgm.sql` calls, which aren't fallbacks), and leaves out owners, grants, publications,
  subscriptions and the migrations table. Objects that belong to an extension are left to
  `CREATE EXTENSION`.
- Materialized views are created with their data, from the tables as they are when the
  migration runs; the header says so when there are any.
- If your configuration sets `decamelize: true`, `baseline` refuses identifiers that
  `decamelize` would rename when the migration runs, i.e. any with an uppercase letter such as
  `LegacyCustomer` (`INVALID_OPTIONS`, naming them). Write that database's baseline with
  `--format sql`, which `decamelize` doesn't change.

### What Becomes a `pgm` Call

Schemas (`createSchema`), extensions (`createExtension`), enums and composite types
(`createType`), domains (`createDomain`), sequences (`createSequence`), tables with their
columns, identity and stored generated columns and comments (`createTable`), the defaults and
`NOT NULL` that an inheritance child gives the columns it inherits (`alterColumn`),
constraints (`addConstraint`, with PostgreSQL's own definition), indexes (`createIndex`),
views and materialized views (`createView`, `createMaterializedView`), functions
(`createFunction`), triggers (`createTrigger`), row-level security and policies (`alterTable`,
`createPolicy`), casts (`createCast`) and operators (`createOperator`).

### Fallbacks

What the `pgm` operations can't express is written as raw SQL, `pgm.sql(…)`, under a
`// fallback: <reason>` comment (several reasons are separated by commas). `baseline` prints
one warning with the number of fallbacks. With `--strict`, it writes nothing and fails with
`UNSUPPORTED_OBJECTS` instead, listing every such object and why.

| Object            | Reasons                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Table             | The whole `CREATE TABLE` becomes raw SQL for `partition`, `virtual generated column` (PostgreSQL 18), `storage parameters`, `access method` (not heap), `multiple inheritance`, `identity sequence name` (not `<table>_<column>_seq`), `NOT NULL constraint name` (not the default one), `column settings` (a column's statistics target, storage, compression or options) and `replica identity` (`FULL` or `NOTHING`); and for what `createTable` can't write: `partition key` (an expression, a collation or an operator class in it), `NOT NULL NO INHERIT` and `NOT NULL NOT VALID` (PostgreSQL 18), `bigint option` and `zero option` (identity options beyond `Number.MAX_SAFE_INTEGER`, or `0`), `column order` (column names like `'1'`, which an object would put first), `no columns` and `line break` (in a column). A table otherwise written with `createTable` gets `comment on column` for a comment on a column it only inherits, and `comment on sequence` for a comment on an identity sequence. |
| Index             | `index method <method>` (not `btree`, `hash`, `gist`, `spgist` or `gin`), `operator class`, `collation`, `nulls order`, `storage parameters`, `partition index name` (an index of a partition, attached to this one, that has another name than PostgreSQL would give it), `CLUSTER ON`, `replica identity` (the table's `REPLICA IDENTITY USING INDEX`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Function          | `procedure`, `SQL-standard body`, `leakproof`, `cost or rows` (not the defaults), `language c` and `language internal`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Trigger           | `UPDATE OF columns`, `transition tables`, `firing mode` (a trigger that is disabled, or enabled for `REPLICA` or `ALWAYS`), `referenced table` (a constraint trigger's `FROM`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Policy            | `restrictive policy`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Domain            | `several constraints`, `NOT VALID constraint`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Composite type    | `attribute collation`, `attribute order` (attribute names like `'1'`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Sequence          | `unlogged sequence`, `bigint option` (a value beyond `Number.MAX_SAFE_INTEGER`), `zero option` (a `0` that `createSequence` would leave out).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| View              | `view options` (an option `createView` can't express).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Materialized view | `storage parameters`, `access method`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Operator          | `operator schema` (a schema that needs quotes), `commutator or negator` (in another schema).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Constraint        | `CLUSTER ON`, `replica identity` (on the constraint's index), `line break` (in the definition).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Always            | Range types (`range type`), collations (`collation`), aggregates (`aggregate`), rules (`rule`), extended statistics (`extended statistics`), and comments on anything but tables and columns (`comment on <type>`, e.g. `comment on view`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

A partition's own key constraint with another name than PostgreSQL would give it is added
before the partitioned table's, with `addConstraint` (not a fallback), so that the
partitioned table's key attaches it instead of creating one with another name.

For example, the [Pagila](https://github.com/devrimgunduz/pagila) sample database gets 56
fallbacks, its 55 partitions and one aggregate, while
[Chinook](https://github.com/lerocha/chinook-database) gets none.

### Not Supported

Some objects can't be written as a TypeScript or JavaScript migration at all: access methods,
base types, conversions, event triggers, foreign data wrappers, foreign servers and foreign
tables, procedural languages, operator classes and operator families, ordered-set aggregates,
text search configurations, dictionaries, parsers and templates, and transforms. When the
database has any that don't belong to an extension, `baseline --format ts` fails with
`UNSUPPORTED_OBJECTS` and lists them: use the SQL baseline for that database.
